# ESP32-S3 模拟校园一卡通

用 ESP32-S3 N16R8、RC522 和 OLED 制作一台模拟校园卡终端：微信小程序通过 BLE 开卡、增加虚拟余额、消费、查询卡片与流水，并设置 OLED 字号和展示效果。

**金额均为虚拟演示余额，界面中的“元 / 分”只是计量方式，不接入真实支付。只在同一台设备和自己准备的空白测试卡上使用；首版不提供退款。**

## 硬件与接线

默认开发板为 ESP32-S3 N16R8（16 MB Flash、8 MB OPI PSRAM），OLED 为 SSD1306 128×64 I²C。N16R8 不能唯一确定开发板引脚布局，接线前请核对你的板子是否引出了这些 GPIO、是否已被其他外设占用。

断电后按模块上的引脚名称连接。以下数字都是 GPIO 编号，不是排针序号。

| 模块 | 模块引脚 | ESP32-S3 |
| --- | --- | --- |
| OLED | VCC / GND | 3V3 / GND |
| OLED | SDA | GPIO8 |
| OLED | SCL / SCK | GPIO9 |
| RC522 | 3.3V / GND | 3V3 / GND |
| RC522 | SDA / SS | GPIO10 |
| RC522 | SCK | GPIO12 |
| RC522 | MOSI | GPIO11 |
| RC522 | MISO | GPIO13 |
| RC522 | RST | GPIO14 |
| RC522 | IRQ | 不连接 |

RC522 模块上标记为 `SDA` 的脚在本项目 SPI 接法里是 **片选 SS**，不要接到 OLED 的 SDA。两模块共地，均使用 3.3V；避免 OLED 模块的 I²C 上拉接到 5V。若 OLED 不是 SSD1306 128×64，需要先修改驱动配置。

## 测试卡与数据区域

仅支持自己拥有、可擦写、使用默认 Key A `FF FF FF FF FF FF` 的 MIFARE Classic 1K / 4K 空白测试卡。不支持把现有学校校园卡、银行卡、交通卡或加密门禁卡拿来充值；“13.56 MHz”也不代表所有卡型都兼容。

本项目已指定的待实测卡片为 **S50 空包卡、S50 异形卡**。S50 通常指 MIFARE Classic 1K 或兼容芯片，使用 13.56 MHz、ISO/IEC 14443 Type A；以读卡器实际识别结果为准。两种外形共用现有固件和数据布局，分别开卡、分别保存余额。卡片的扇区必须可用全 FF Key A 认证，且本项目使用的数据块初始为空白（字节为 00 或 FF）；商品名中的“空包”不自动保证这些条件。异形卡天线尺寸和位置可能不同，测试时单张靠近 RC522 天线区域，保持到写入并回读完成。参考 [NXP Classic 1K 数据手册](https://www.nxp.com/docs/en/data-sheet/MF1S50YYX_V1.pdf)。

开卡和交易会覆盖下面列出的数据块。测试前确认卡上没有需要保留的资料。

| 内容 | 使用的数据块 |
| --- | --- |
| 快照槽 0，96 字节 | 4、5、6、8、9、10 |
| 快照槽 1，96 字节 | 12、13、14、16、17、18 |

固件不写块 0，也不写各扇区最后的 trailer 块，不修改卡片密钥和访问控制位。两个快照槽交替保存身份、余额和序号；更新前先把待确认交易写入 ESP32 的 NVS，更新另一槽后回读校验，确认成功才提交流水。移卡或断电造成结果未确认时，保留待恢复交易，重新刷原卡完成恢复，不直接再加款或扣款。

这套实现用于理解卡片存储和交易恢复：**不防卡片克隆、恶意篡改和多台终端间的旧余额回滚**。BLE 默认没有配对认证，附近的兼容客户端可以连接操作。不要把演示余额当成有实际价值的账户，也不要在存在待确认交易时擦除 NVS 或更换终端；恢复依赖原设备的交易记录。

## 编译与烧录

安装 PlatformIO IDE，或让 `pio` / `platformio` 命令可用。在本目录执行：

```powershell
.\tools\build.ps1
```

脚本先查找 PATH 中的 PlatformIO，再查找当前用户的 `.platformio\penv\Scripts\platformio.exe`；默认只编译，不烧录。可用 `-Clean` 先清理此环境的构建产物。

如需复用完整的本地工具链缓存，可在 `.local/platformio-packages.txt` 中填写包目录。脚本读取这个可选文件，临时设置本次进程的 `PLATFORMIO_PACKAGES_DIR`，执行结束后恢复原值，不修改系统环境变量。正常安装 PlatformIO 时无需此文件；`.local/` 不应提交或随源码分发。若缓存失效，更新文件中的目录，或删除该可选文件后使用正常安装的工具链。直接运行 `pio` 不会读取这份本地配置。

成功构建会导出 `output/firmware.bin`。它只是应用固件，不是包含 bootloader、分区表和 NVS 的整片 Flash 镜像，不应作为整片镜像写入地址 0。确认接线和实际串口后执行以下命令烧录，例如端口为 COM6：

```powershell
.\tools\build.ps1 -UploadPort COM6
```

只有显式传入 `-UploadPort` 才会烧录。脚本交给 PlatformIO 按项目分区和烧录地址上传，避免手工错用应用镜像。普通环境也可直接在 PlatformIO 中选择 `esp32-s3-n16r8` 环境，或使用：

```powershell
pio run -e esp32-s3-n16r8
pio device list
pio run -e esp32-s3-n16r8 --target upload --upload-port COM你的端口
pio device monitor --baud 115200 --port COM你的端口
```

上传会替换开发板原固件；在分区与数据结构兼容时，常规 PlatformIO 上传保留 NVS。若无法进入下载模式，按住 BOOT、点按 RST/EN，再松开 BOOT，然后重新上传。更换分区、擦除 Flash 或清空 NVS 会影响本地记录及未完成交易的恢复。

## 导入微信小程序

公开的 `miniprogram/` 只使用占位 AppID。使用 Python 3.9 或更新版本生成本机副本：

```powershell
python .\tools\prepare_wechat.py --appid 你的微信小程序AppID
```

也可设置环境变量 `WECHAT_APPID`，再运行不带参数的脚本。合法 AppID 格式为 `wx` 加 16 位十六进制字符。脚本不输出 AppID，不修改公开源码；输出固定在本项目 `.local/wechat/`，重新运行只替换此目录。不要把手工修改仅保存在生成副本中，更新源码后应再次生成。

1. 在微信开发者工具导入 `.local/wechat/`，使用拥有该 AppID 开发权限的微信账号。
2. 管理员在小程序管理后台“用户隐私保护指引”中配置蓝牙相关用途；源码中的权限声明不能代替后台配置。
3. 用手机微信真机预览，完成隐私同意、蓝牙授权，并打开手机蓝牙。按系统提示允许微信的蓝牙 / 附近设备权限；部分安卓机还需要定位服务或定位权限。
4. 搜索并连接 `S3-CAMPUS-XXXX`。无须先在手机系统蓝牙设置中配对。微信开发者工具模拟器不能代替真实 BLE 连接验收。

若报 `api scope is not declared in the privacy agreement`，先检查当前 AppID 后台隐私配置及其生效状态，再重新预览。若发现不了设备，核对串口启动输出、手机宿主微信的系统权限，并确认没有另一台手机或 BLE 调试工具占用连接。OLED 和 RC522 的就绪状态以小程序返回的设备状态为准，物理接线修复后重启再检查。

## 使用流程

1. **开卡**：输入姓名和学号，点击开卡，30 秒内刷空白测试卡。初始虚拟余额为 0。姓名最多 24 个 UTF-8 字节，学号最多 16 字节。
2. **充值**：输入虚拟金额，启动充值任务，再刷目标卡；写入并回读确认后显示成功与新余额。
3. **消费**：输入金额和场景（例如“食堂”），启动消费任务，再刷卡。余额不足时拒绝消费并保留原余额。
4. **查询**：没有等待任务时刷卡，只读取卡片信息；小程序可查看最近最多 20 笔完整交易结果。
5. **屏幕**：可设置金额数字的 12 / 16 / 24 / 32 字号、静态 / 上滑 / 逐字效果、1500–10000 毫秒展示时长。中文标签使用固定的 12 像素字库；逐字效果作用于金额。所有效果下，超宽金额都会降为 16 像素完整显示；上滑模式支持长中文标签横向滚动，其他模式的长标签可能截断。设备持久化保存这些设置，实际显示效果需真机核对。

金额在协议和设备内部使用整数“分”，例如 12.50 对应 `amountCents:1250`，避免小数计算误差。单笔金额范围为 1–100000000 分，场景最多 24 个 UTF-8 字节。

若发送在终端收到完整请求前中断，手机仍会保留原业务编号。先点击“核对原订单”；设备无待办且查不到结果时，可手动选择“重发原订单（同编号）”，只续办刚才中断的订单，保留原金额、资料和编号。已有结果或待确认交易不会重新下单。已处理但明细过期时按提示刷卡查询余额。该功能用于近期中断恢复，设备的保留窗口见 [docs/CARD_FORMAT.md](docs/CARD_FORMAT.md)。

等待刷卡超过 30 秒，任务失效；写入尚未开始时可以取消。已经进入“结果未确认”的交易不能取消，也不能创建另一笔交易：保持或重新放回原卡，等待恢复结果。不要用新的充值或消费操作来“补一次”。

断线或 15 秒内未收到完整回应，只表示客户端尚未确认。重新连接后以原业务 id 查询结果；确认结果前不显示成功、不生成新 id 再次扣款。卡片一直放在读卡器上不会不断触发新交易；完成后移开卡，下一笔业务应由新的操作启动。

流水的 `timestamp` 只有设备完成校时后才有意义；未校时为 0。小程序应显示“设备未校时”或注明接收时间，不能将手机收到通知的时间伪装成精确交易发生时间。

## 协议和验收

BLE 服务、分包格式、请求字段和错误恢复规则见 [PROTOCOL.md](PROTOCOL.md)。本项目协议与 OLED 文字屏示例不同，需要配套使用本项目固件和小程序。

安装 Node.js 后，可在项目目录运行软件测试：

```powershell
npm test
npm run test:core
npm run test:transport
```

核心与传输测试需要可用的 C++ 编译器，具体以测试脚本的编译器检查为准；这些测试不要求连接开发板。

按 [docs/ACCEPTANCE.md](docs/ACCEPTANCE.md) 完成余额不足、移卡、重复请求、断线和断电恢复测试。**编译通过与软件逻辑验证不代表已完成你的开发板、卡片和手机上的硬件验收。**
