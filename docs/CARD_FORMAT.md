# 卡片数据与交易恢复

这是单台 ESP32 管理自己测试卡的校园卡演示。余额单位是整数分，上限 `100000000` 分；开卡初始余额为 0。CRC 用于发现意外损坏，不是防伪认证、加密或支付安全机制。

## 支持与保留区域

使用支持默认 `FF FF FF FF FF FF` Key A 的 MIFARE Classic 1K/4K 测试卡。首次开卡要求下述两个槽内的数据均为 `00`/`FF`。非空且不能识别的卡不会被自动格式化。

每个快照 96 字节，由六个 16 字节用户块组成：

| 槽 | 按顺序读取、写入的块号 |
| --- | --- |
| A | 4、5、6、8、9、10 |
| B | 12、13、14、16、17、18 |

不写 block 0、不写任何扇区尾块，不修改 UID、密钥或访问条件。Classic 1K 每扇区最后一块（3、7、11……）是尾块。测试卡在这些数据块有其他用途时请换空白卡。

## 快照格式

所有多字节整数为小端序；姓名、学号采用 UTF-8。固定文本字段不存末尾 NUL，解码后由固件在内存中补 NUL；剩余字节填 0。

| 偏移 | 长度 | 内容 |
| --- | --- | --- |
| 0 | 4 | ASCII `CAMP` |
| 4 | 1 | 格式版本 1 |
| 5 | 3 | 保留，0 |
| 8 | 4 | 自定义卡号，从 10000001 开始 |
| 12 | 4 | 余额，非负有符号整数分 |
| 16 | 4 | 交易序号，开卡为 0，成功充值/消费后加 1 |
| 20 | 8 | 最近成功业务 ID，非零 64 位整数 |
| 28 | 4 | UID 绑定 CRC32，输入为 UID 长度 1 字节＋UID 原始字节 |
| 32 | 24 | 姓名 UTF-8，最多 24 字节 |
| 56 | 16 | 学号 UTF-8，最多 16 字节 |
| 72 | 20 | 保留，0 |
| 92 | 4 | 前 92 字节 CRC32/ISO-HDLC |

单槽首先检查 magic、版本、CRC、UID 绑定、余额范围和 UTF-8。两个槽都有效时，卡号、姓名、学号必须一致，交易序号必须相邻；若序号相同，两个快照必须逐字节完全一致。以较新序号为当前记录。

只剩一个有效槽时可读取它，但设备还会对比本机保留的已确认序号和快照摘要：不能接受比本机记录更旧的余额，也不能接受相同序号、不同内容的快照。此检查仅覆盖本机最近保留的 16 张卡。

## 写入与恢复

1. 小程序先创建业务 ID，并发送开卡/充值/消费等待任务。ESP32 在 NVS 中保存任务。等待阶段不写卡，30 秒未刷卡会产生持久化的过期结果；重启后尚未开始的等待任务同样记为过期。
2. 刷卡后读取两个槽。校验余额、金额与序号，计算唯一的新快照。
3. 在修改卡片前，先把原卡 UID、当前快照、目标槽原始内容、完整目标快照和原始交易时间保存到 NVS journal。保存失败则卡片不写入。
4. 写入非当前槽；开卡使用 A 槽。六个块按表中顺序写入，含 CRC 的最后一块最后写。旧槽始终保留。
5. 回读新槽，逐字节对比完整目标快照。只有回读完全相同，并且本地流水提交成功后，才报告成功并清除 journal。
6. 写卡、回读或最终流水提交遇到异常时保留 journal。禁止取消或启动其他业务，提示移开后重刷原卡。
7. 重刷时如果目标槽已经等于 journal 的目标快照，只补交本地流水，不再加减余额；如果当前旧槽仍完好、目标槽尚未完成或仍是原来的旧目标槽，则重新写入同一份完整目标快照。不是再次计算、扣款。
8. 原卡 UID 不符或发现其他有效但不属于本次业务的快照时，保持待确认并拒绝覆盖。保留卡片和设备以便排查。

开卡写到一半时，同样可以使用 journal 恢复，不需要自动清卡。设备 NVS 损坏/丢失后无法保证恢复尚未确认的写入；固件不会静默重置存在但无效的持久状态。

## 业务 ID 与记录保留

- 开卡、充值、消费、余额不足、取消、过期等终态均可通过 `result(id)` 查询。
- 最近 20 个终态保存完整明细；最近 96 个终态额外保存业务 ID 和参数摘要。重复请求参数一致则返回原结果；参数不同则返回 `ID_CONFLICT`。
- 业务 ID 还在 96 笔去重窗口、完整明细已经淘汰时返回 `RESULT_EXPIRED`，拒绝重放，并要求查询当前余额。
- 卡片还保留最后一个成功业务 ID，即使本机去重条目被淘汰，也会拒绝把相同 ID 再次用在该卡的下一笔交易。
- 这是有界存储，**不提供永久去重或多设备账务一致性**。设备关闭/重连后先查询原业务；不要为一次结果不明的交易随意生成新 ID。进行超过 96 笔业务后的历史补单，或同一卡在多台设备同时交易，不属于首版支持的流程。

本地 `campus::State` 为带版本与 CRC 的可复制结构，当前主机构建大小 4128 字节。ESP32 的 NVS 适配层必须检查 `getBytesLength`、`getBytes`、`putBytes` 完整长度。成功流水记录使用首次准备 journal 时的时间；设备未校时时为 0，不编造交易日期。

## 自动验证

运行 `node tools/test-core.js`，使用本机 C++ 编译器编译并执行内存卡/存储故障注入测试。覆盖正常开卡充值消费、重复业务及参数冲突、取消/过期、余额不足/金额上限、未知卡、各块写入中断及断电、写完后回读失败、写前 NVS 失败、写后 NVS 提交失败、重启恢复、历史窗口、旧快照回放和同序号内容变化。

这些测试验证业务和恢复算法，不能替代 RC522 射频环境、实际卡片写入和 OLED 的真机验收。
