# 性能与稳定性复查

日期：2026-11-07。本记录区分代码和主机验证，与尚待进行的实体卡、手机、USB及功耗实测。

| 问题 | 修改 | 验证 |
| --- | --- | --- |
| OLED 画面不变也每65ms整屏发送，持续占用I²C | 先比较动画相位，再比较1KB帧缓存；内容不变不发送；逐字金额使用栈缓冲 | 发送次数、静态页、睡眠/唤醒及动画边界主机测试 |
| 650ms处对没有开场动画的页面也扣除时间，逐字可能倒退 | 只对实际播放的成功/失败开场计算偏移 | 无开场、静态、650ms前后及计时回绕回归 |
| 等待任务超时但NVS保存失败，循环不断重试4KB账本并发事件 | 失败后1秒退避，只有成功保存终态才通知；启动恢复失败禁交易 | 连续500次循环故障注入；恢复与启动fail-closed |
| 流水大包慢且4KB上限让后面的记录不可达 | 最多5条/页、快照revision验证、整轮完成后原子更新列表；BLE/USB快照独立 | 20条遍历、翻页期间数据变化、过期重拉及中途失败 |
| 状态事件排队会拖慢业务回应 | 未开始发送的事件合并，回应优先；已开始的正文完整发送，不交错；队列最多3条 | 有界队列、FIFO回应、部分正文不抢占测试 |
| 旧BLE回应或坏事件影响新RPC，原生写悬挂后仍可开始新请求 | 会话/消息编号过滤，事件独立组包；悬挂写超时关闭旧会话，关闭也有上限 | 微信和PC模拟原生写永不回调、迟到回调、重连和组包回归 |
| 卡读写期间断开重连，旧队列可能发到新连接 | 发送前再次核对epoch，清除旧分包，RPC回应绑定原epoch | 代码路径复查及旧会话回归 |
| 小程序同一RPC重复applyState、多次setData，重复RSSI刷新整表 | 回应只应用一次，状态和业务锁合并更新，相同广播不刷表 | 页面调用次数及扫描生命周期回归 |
| RFID存在探测和HALT沿用25ms超时，延迟主循环其它任务 | 仅WUPA/HALT使用约3ms短帧计时，RAII恢复原reload值；鉴权/读写保留原值 | 超时寄存器恢复主机测试；S50实物稳定性待测 |
| USB瞬时就绪波动导致半条JSON丢失 | 短暂无就绪只暂停；首次观察到断开后持续200ms再清会话 | 短暂波动、长任务后首次false及时间回绕测试 |

每笔正常充值/消费仍保留读卡、写前journal、写卡回读和流水提交。没有为降低写入次数而跳过余额确认。账本和卡片格式保持兼容；电源设置独立保存。

新增的诊断接口返回实际设备运行时长、堆内存、最大循环耗时、最近读写耗时及发送队列长度，便于接线后记录真实数据。浏览器演示的耗时不能用来代表RC522速度、BLE速度或电池续航。
